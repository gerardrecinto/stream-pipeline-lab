The windowing definition

Window.<Event>into(FixedWindows.of(Duration.standardMinutes(1)))
    .triggering(AfterWatermark.pastEndOfWindow()
        .withLateFirings(AfterPane.elementCountAtLeast(1)))
    .withAllowedLateness(Duration.standardMinutes(2))
    .accumulatingFiredPanes()

What I ran into

Beam's Distinct breaks event-time windowing when it runs before windowing: it groups in the global window and re-stamps every element at the end of time, so all events collapsed into one window. Applied after a triggered window it would re-emit accumulated elements on each late pane. I replaced it with a per-id stateful step inside the window.

Pane timing differs by runner. Flink in batch mode left pane timing UNKNOWN where the DirectRunner reported ON_TIME, so the cross-runner check compares the data and not the pane label.

The stateful dedupe step changed the on-time and late split on the DirectRunner: the late event was folded into the on-time pane. With the step removed the panes split as expected, so the pane demo runs without it and dedupe is tested separately. I did not find out whether that is documented runner behavior or a flaw in my test.

Not run: Apache Spark, Kafka (see my kafka-ops-lab repo for Kafka), a real cluster, and timing comparisons. The first run in a JVM pays class loading, so the millisecond figures in the data file are not a benchmark.
